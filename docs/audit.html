Методология

Score(repo) = 100 − (Critical×12 + High×6 + Medium×2 + Low×0.5), floor 0

Overall = Score(back)×0.5 + Score(zhancareai)×0.3 + Score(academy)×0.2

Веса по severity отражают разницу в реальной эксплуатируемости: CRITICAL-находки в этом проходе — это рабочие цепочки захвата аккаунта/денег в несколько запросов, а не теоретический риск, поэтому штраф за них доминирует в формуле. Веса по репозиториям — backend держит PHI и платежи для обоих фронтендов одновременно, поэтому его проблемы бьют по всей системе сразу.

1. Захардкоженные продакшен-секреты в settings.py — включая SECRET_KEY (подписывает все JWT), пароль БД, ключи Mistral/LiveKit/TipTopPay, пароль почты. Утечка = подделка токена под любого пользователя, прямой доступ к БД. mchs_back/settings.py
2. TipTopPay webhook фейлится в «открыто» (fail-open) — если заголовок HMAC просто отсутствует или секрет не задан, подпись считается валидной. 3. Гостевой вход по access_code — без throttling — 6-значный код (не CSPRNG) при совпадении сразу выдаёt полноценный RefreshToken пациента — захват аккаунта со всей медкартой. Брутфорс ничем не ограничен. consultations/views.py:1420-1488
4. IDOR в профиле пользователя — любой авторизованный пользователь может прочитать и перезаписать профиль любого другого пользователя по ID, без проверки владения или роли. common/views/profile.py:96-108, 163-178
5. Живые секреты закоммичены в git (zhancareai) — Mistral API key и Sentry auth token лежат в трекаемом .env (не в .gitignore, который исключает только .env*.local). Считать утёкшими — ротация обязательна. zhancareai/.env:1-3
Плюс заметная системная проблема: миграция на httpOnly cookie для zhancare-academy-refined технически не работает — apiLogin/ apiRefreshToken используют голый fetch() без credentials: "include", поэтому cookie zha_access/zha_refresh скорее всего никогда не выставляются для пользователей academy. Плюс ни в одном из трёх репозиториев нет CSRF-защиты для cookie-флоу — закрыть до того, как backend начнёт принимать cookie как единственный фактор аутентификации где-либо.

5Методология и процесс аудита

Чем именно был этот аудит, чем не был, кто и как его проводил — чтобы результат можно было корректно интерпретировать и доверять цифрам выше.

Тип аудита

✓ Это было

  • White-box статический ревью кода — полный доступ к исходникам трёх репозиториев
  • Read-only — ни один файл не менялся в процессе проверки
  • Ручное (агентом) прочтение кода с целевыми чек-листами по категориям риска (см. ниже), а не прогон одного готового SAST-инструмента
  • Severity по OWASP-style шкале влияния: CRITICAL / HIGH / MEDIUM / LOW — та же шкала, что используется в стандартах код-ревью проекта

✕ Этого не было

  • Динамической эксплуатации (pentest) — находки не подтверждались реальной атакой на работающий стенд, только анализом кода
  • Проверки сетевого/инфраструктурного слоя — firewall, k8s/Helm-конфиги, сетевые ACL, права доступа к серверам
  • Фактического запуска npm audit / pip-audit / safety check — версии зависимостей оценивались визуально по package.json/requirements.txt
  • Аудита сторонних SaaS-сервисов (Sentry, LiveKit, Yandex Cloud) и их собственных security-настроек
  • Социальной инженерии, фишинг-симуляций, нагрузочного/DoS-тестирования

Кто и как проверял

Три независимых агента security-reviewer запущены параллельно — по одному на репозиторий, без общего состояния между собой. Инструменты каждого агента: Read, Grep, Glob, Bash (для команд типа grep -i csrf, проверки версий пакетов) — то есть только локальное чтение/поиск кода, без сетевых запросов и без записи. Каждому агенту перед стартом был передан явный чек-лист по репозиторию и уже известный контекст из предыдущих проходов (например, какие пункты из JWT-хардения уже закрыты — раздел «Авторизация»), чтобы не тратить ресурс на повторное обнаружение уже решённого и не задвоить находки.

Контроль качества результата

Каждый агент обязан указывать точный файл:строка на каждую находку (не общие рассуждения) и формулировать конкретный фикс, а не «исправьте это». Перед публикацией результаты трёх агентов вручную сверены на дублирование и перенесены в эту страницу без изменения сути находок. Числовая ИБ-оценка (раздел выше) — отдельный шаг, посчитанный по фиксированной формуле от итоговых количеств находок, а не назначенный на глаз.

Про «prompt injection» в логах агентов: два из трёх агентов пометили часть содержимого инструментов как похожее на инъекцию промпта — блоки с правилами кодстайла/тестирования, подгруженные через system-reminder. На деле это штатный механизм окружения: личные правила пользователя из ~/.claude/rules/ecc/* автоматически подмешиваются в контекст после части вызовов инструментов. Агенты не были в курсе этой особенности окружения и подняли ложную тревогу — ни один из них не последовал инструкциям из этого блока, реальной угрозы не было.
Главное ограничение метода: статический ревью находит «что выглядит небезопасным в коде», но не гарантирует, что все найденные пути реально достижимы в проде (например, может быть compensating control на уровне инфраструктуры, который агент не видел — балансировщик, WAF, сетевые правила). И наоборот — статический анализ может пропустить уязвимости, которые проявляются только в runtime-конфигурации или во взаимодействии нескольких сервисов. Эта страница — приоритизация для инженерной команды, не итоговое заключение для соответствия конкретному стандарту (ISO 27001, HIPAA и т.п.).

6Итоговая оценка риска

zhancare-back

Несколько CRITICAL-проблем образуют реальные цепочки захвата аккаунта и мошенничества с платежами: захардкоженные секреты (включая ключ подписи JWT) в git, брутфорсимый вход по access_code сразу выдающий токен, webhook платежей, пропускающий запросы без подписи, и IDOR, позволяющий читать/менять профиль любого пользователя. Эксплуатация — несколько curl-запросов, без специальных знаний. С учётом PHI и живых платежей это блокеры до следующего деплоя.

zhancareai

Главное — утечка живых ключей (Mistral, Sentry) в закоммиченный .env, считать их скомпрометированными. Второе — полное отсутствие CSRF-защиты обесценивает недавно добавленную cookie-аутентификацию: переход на httpOnly cookie без CSRF-токена меняет один риск (кража токена через XSS) на другой (CSRF на чувствительные действия). XSS в карте клиник на admin-странице — точечная, но реальная дырка. Остальное — в порядке.

zhancare-academy-refined

Самое значимое: миграция на httpOnly cookie для этого фронтенда фактически не работает — apiLogin/apiRefreshToken не отправляют credentials, так что cookie, скорее всего, не выставляются вообще, и весь поток молча продолжает работать на чистом localStorage-токене. В сочетании с полным отсутствием CSRF это создаёт хрупкую границу доверия: всё держится только на том, что backend пока требует заголовок Authorization, а не доверяет cookie как самостоятельному фактору. Приоритет: сначала credentials-фикс, затем письменное подтверждение от backend-команды про cookie-vs-header, затем — серверный гейт на admin-страницу курсов/категорий.

Рекомендуемый порядок исправлений: ротация всех секретов (back + zhancareai) → фикс TipTopPay fail-open → throttling/CSPRNG для access_code → фикс IDOR в профиле → credentials-фикс в academy login → CSRF во всех трёх репозиториях → валидация загрузки медицинских документов → остальное (MEDIUM/LOW) по мере появления времени в спринте.
