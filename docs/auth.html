1Архитектура системы

Авторизация построена на классическом паттерне access + refresh JWT, но с двумя нестандартными добавками: привязкой токена к записи сессии (UserSession) для возможности видеть и отзывать устройства, и отдельным механизмом одноразовых magic-link токенов для гостевого доступа к видеоконсультациям без полноценной регистрации.

Backend — Django

rest_framework_simplejwt выпускает access/refresh токены. Каждый refresh-токен регистрируется как отдельная строка UserSession (устройство, IP, user-agent). Кастомный класс аутентификации проверяет, что сессия ещё активна при каждом запросе.

Frontend — Next.js

Токены лежат в localStorage. Axios-интерсептор подвешивает Authorization: Bearer на каждый запрос и автоматически обновляет access-токен при 401, используя единый refreshPromise, чтобы не плодить параллельные запросы на рефреш.

Ключевая идея: JWT сам по себе stateless, но ZhanCare добавляет слой состояния через UserSession — это позволяет реализовать «выйти со всех устройств», отследить, с какого IP/устройства был логин, и мгновенно инвалидировать сессию без ожидания истечения токена.

3CustomJWTAuthentication

zhancare-back/common/authentication.py

Стандартный JWTAuthentication из simplejwt проверяет только подпись и срок жизни токена. ZhanCare расширяет его проверкой сессии — если пользователь нажал «выйти со всех устройств» или сессию отозвал админ, токен технически ещё валиден по подписи, но запрос всё равно будет отклонён. 

class CustomJWTAuthentication(JWTAuthentication):
    def get_validated_token(self, raw_token):
        validated_token = super().get_validated_token(raw_token)

        # Magic-link токены (см. раздел 10) никогда не принимаются как
        # обычный bearer-токен — иначе их можно было бы переиграть на любой эндпоинт.
        if validated_token.get('access_type') == 'magic_link':
            raise InvalidToken('Magic-link tokens cannot be used as bearer tokens')

        session_jti = validated_token.get('session_jti')

        if session_jti:
            cache_key = session_cache_key(session_jti)

            # Кэш-хит — доверяем без обращения к БД
            if cache.get(cache_key):
                return validated_token

            try:
                session = UserSession.objects.get(
                    refresh_token_jti=session_jti,
                    is_revoked=False,
                    is_deleted=False
                )
                # last_activity обновляется только на кэш-мисс — естественно
                # раз в SESSION_CACHE_TTL, а не на каждый запрос
                session.last_activity = timezone.now()
                session.save(update_fields=['last_activity', 'updated_at'])
                cache.set(cache_key, True, timeout=SESSION_CACHE_TTL)  # 45 сек

            except UserSession.DoesNotExist:
                raise InvalidToken('Session has been revoked or expired')

        return validated_token

    def authenticate(self, request):
        try:
            result = super().authenticate(request)  # заголовок Authorization
        except (InvalidToken, AuthenticationFailed):
            result = None

        if result is not None:
            return result

        # Заголовка нет/невалиден → fallback на httpOnly cookie zha_access
        raw_token = request.COOKIES.get(settings.AUTH_ACCESS_COOKIE_NAME)
        if not raw_token:
            return None

        try:
            validated_token = self.get_validated_token(raw_token)
            return self.get_user(validated_token), validated_token
        except (InvalidToken, AuthenticationFailed):
            return None
Что изменилось: раньше проверка сессии делала запрос к БД на каждый авторизованный вызов. Теперь результат кэшируется на 45 секунд (cache.set/cache.get, backend — Redis через django-redis, если задан REDIS_URL, иначе локальный in-memory кэш). Кэш явно инвалидируется при logout() (раздел 7) и при ротации refresh-токена (раздел 6), так что отзыв сессии видим практически мгновенно, а не только по истечении TTL.
Dual-mode авторизация: authenticate() сначала пробует заголовок Authorization: Bearer — этот путь остаётся рабочим навсегда, он обязателен для desktop-приложения на Tauri (zhancare.app / tauri.localhost), которое не может получить cookie с доменом .zhan.care (другой регистрируемый домен). Если заголовка нет — пробует httpOnly cookie zha_access, выставляемую при логине/рефреше (раздел 13).

Каждый refresh-токен = отдельная строка в этой таблице. Поэтому у одного пользователя может быть N активных сессий (телефон, ноутбук, планшет) — каждая со своим refresh_token_jti, IP и user-agent. В профиле пользователь видит список «Активные устройства» и может отозвать любое из них точечно, не разлогинивая себя на текущем.

Создание токенов при логине

zhancare-back/common/serializers/user_session.py
def create_jwt_tokens_for_user(user, request=None, device_name=None):
    device_type, auto_device_name = parse_device_info(user_agent_string)
    ip_address = get_client_ip(request)

    refresh = RefreshToken.for_user(user)
    refresh_jti = str(refresh['jti'])

    session = UserSession.objects.create(
        user=user,
        refresh_token_jti=refresh_jti,
        device_name=device_name or auto_device_name,
        device_type=device_type,
        user_agent=user_agent_string,
        ip_address=ip_address,
    )

    access = refresh.access_token
    access['session_jti'] = refresh_jti  # ← кастомный claim, см. раздел 3

    return {
        'access_token': str(access),
        'refresh_token': str(refresh),
        'session_id': session.id,
    }
Связь устроена через JTI refresh-токена (JSON Token ID, уникальный идентификатор внутри payload) — он одновременно служит первичным ключом записи UserSession и значением claim'а session_jti внутри access-токена. Так access-токен «знает», к какой сессии он принадлежит, без лишнего запроса к refresh-токену.

6Обновление токена (refresh) и ротация

POST /api/v1/auth/token/refresh/ — common/views/auth.py::token_refresh_view
Найденный и исправленный баг: этот эндпоинт раньше был зарегистрирован на стоковый rest_framework_simplejwt.views.TokenRefreshView, который ничего не знает про UserSession. После первого же рефреша UserSession.refresh_token_jti навсегда указывал на уже заблокированный (blacklisted) JTI, а новый access-токен вообще не получал claim session_jti — то есть проверка отзыва сессии (раздел 3) молча пропускалась до конца жизни токена. Теперь эндпоинт — тонкая обёртка над refresh_jwt_tokens(), которая действительно синхронизирует сессию. 
def refresh_jwt_tokens(refresh_token_string):
    old_refresh = RefreshToken(refresh_token_string)
    old_jti = str(old_refresh['jti'])

    session = UserSession.objects.get(
        refresh_token_jti=old_jti, is_revoked=False, is_deleted=False
    )  # бросит ValidationError, если сессия отозвана

    old_refresh.blacklist()  # старый refresh сразу недействителен

    new_refresh = RefreshToken.for_user(session.user)
    new_jti = str(new_refresh['jti'])

    session.refresh_token_jti = new_jti   # сессия "переезжает" на новый JTI
    session.last_activity = timezone.now()
    session.save(update_fields=['refresh_token_jti', 'last_activity', 'updated_at'])

    invalidate_session_cache(old_jti)  # старый JTI мёртв — не ждать TTL кэша (раздел 3)

    new_access = new_refresh.access_token
    new_access['session_jti'] = new_jti

    return {'access_token': str(new_access), 'refresh_token': str(new_refresh)}

def token_refresh_view(request):
    # Берёт refresh либо из тела запроса, либо из httpOnly cookie zha_refresh
    refresh_token_str = request.data.get('refresh') or request.COOKIES.get(settings.AUTH_REFRESH_COOKIE_NAME)
    tokens = refresh_jwt_tokens(refresh_token_str)

    response = Response({'access': tokens['access_token'], 'refresh': tokens['refresh_token']})
    _set_auth_cookies(response, tokens['access_token'], tokens['refresh_token'])  # dual-mode, раздел 13
    return response
Почему старый refresh blacklist'ится немедленно? Это защита от повторного использования украденного refresh-токена (replay attack): если злоумышленник перехватил старый токен и легитимный клиент уже обновился — старый токен больше не сработает ни у кого, что сигнализирует о компрометации.

7Логаут и blacklist

POST /api/v1/auth/logout/ — common/views/auth.py
def logout(self, request):
    # refresh_token берётся из тела ИЛИ из httpOnly cookie zha_refresh
    refresh_token = request.data.get("refresh_token") or request.COOKIES.get(settings.AUTH_REFRESH_COOKIE_NAME)
    if refresh_token:
        token = RefreshToken(refresh_token)
        jti = str(token['jti'])

        UserSession.objects.filter(refresh_token_jti=jti).update(
            is_revoked=True, revoked_at=timezone.now()
        )
        invalidate_session_cache(jti)  # ← новое: не ждать TTL кэша, отзыв виден сразу (раздел 3)
        token.blacklist()

    response = Response({"message": "Logged out successfully"})
    _clear_auth_cookies(response)  # ← новое: чистит zha_access/zha_refresh
    return response

Три независимых механизма отзыва срабатывают одновременно:

МеханизмЧто делаетГде проверяется
UserSession.is_revokedПомечает сессию как неактивнуюCustomJWTAuthentication, при кэш-миссе
cache.delete(session_cache_key)Сбрасывает закэшированный «валиден» статусСледующий запрос сразу видит отзыв, не ждёт 45с TTL
token.blacklist()Добавляет JTI в таблицу BlacklistedTokenСтандартный механизм simplejwt при попытке refresh
Дублирование намеренное: blacklist simplejwt защищает конкретно refresh-эндпоинт, а проверка сессии (теперь с кэшем) защищает все авторизованные эндпоинты сразу — даже если у атакующего остался валидный по подписи access-токен на оставшиеся ~15 минут жизни.
Известный edge case (не зафиксировано в этом проходе): если клиент передаёт некорректный/обрезанный refresh_token, RefreshToken(...) бросает исключение, которое ловится широким except Exception — ответ всё равно 200 и cookie очищаются на клиенте, но отзыва сессии на сервере не происходит. Узкий, но реальный риск, если у жертвы протух/потерялся refresh-токен в момент, когда она пытается выйти. Не входило в одобренный объём этой задачи.

8Регистрация

POST /api/v1/auth/register/

Регистрация не выдаёт токены — пользователь должен залогиниться отдельным запросом после создания аккаунта (намеренное разделение, упрощает обработку дублей/валидации без риска выдать токен наполовину созданному юзеру). 

def register(self, request):
    serializer = self.get_serializer(data=request.data)
    if serializer.is_valid():
        if User.objects.filter(Q(email=email) | Q(phone=phone)).exists():
            return Response({"error": "..."}, status=409)

        serializer.validated_data["password"] = make_password(...)
        user = serializer.save()

        user.verified_at = timezone.now()
        user.verification_method = "registration"
        user.save(...)

        # Авто-создание профилей по умолчанию
        if user.is_teacher():
            TeacherProfile.objects.get_or_create(user=user)
        PatientProfile.objects.get_or_create(user=user)

        return Response({"message": "Registration successful!", ...}, status=201)

9Сброс пароля

Трёхшаговый flow через одноразовый 6-значный код с TTL 15 минут.

1
POST /auth/forgot-password/

Генерирует reset_code (6 символов A–Z0–9), пишет reset_code_created_at, отправляет на email

2
POST /auth/verify-reset-code/

Проверяет совпадение кода и что reset_code_created_at не старше 15 минут

3
POST /auth/reset-password/

Устанавливает новый пароль через set_password(), очищает reset_code

Слабое место: 6 символов из 36 (A–Z + 0–9) ≈ 2.2 млрд комбинаций — формально много, но если на эндпоинте verify-reset-code нет rate-limiting, код можно брутфорсить в течение 15-минутного окна. Рекомендация — ограничить число попыток на email/IP (см. раздел 18).

    return str(token)
Реальный пробел (исправлен): ничто не запрещало взять валидный magic-link токен из письма и подставить его как обычный Authorization: Bearer на любой другой эндпоинт API — CustomJWTAuthentication проверял только подпись и сессию, но не claim access_type. Теперь get_validated_token() (раздел 3) явно отклоняет любой токен с access_type == 'magic_link' до того, как дойдёт до проверки сессии — такой токен годится только для одного вызова /consultations/auto-login/.

11WebSocket-авторизация (видеоконсультации, чаты, admin-инбоксы)

zhancare-back/mchs_back/asgi.py, common/websockets/{jwt_auth,middleware}.py
Полностью переделано. Раньше WS-каналы авторизовались легаси моделью rest_framework.authtoken.Token через query-параметр ?token= или сообщение {type:"authenticate"} после того, как соединение уже было принято (accept()) — то есть до явной аутентификации канал был открыт кому угодно. Хуже того, WhatsApp/Telegram admin-инбоксы декодировали JWT с options={"verify_exp": False} — просроченный токен работал против них вечно. Оба недостатка устранены.

Новая схема: middleware на уровне ASGI-роутера

# mchs_back/asgi.py
application = ProtocolTypeRouter({
    "http": get_asgi_application(),
    # AllowedOriginValidator — снаружи: отклоняет handshake с любым
    # Origin, не входящим в ALLOWED_HOSTS, ещё до аутентификации

            URLRouter(consultation_patterns + common_patterns)
        ),
        allowed_hosts=settings.ALLOWED_HOSTS,
    ),

# common/websockets/middleware.py
class JWTCookieAuthMiddleware:
    async def __call__(self, scope, receive, send):
        scope = dict(scope)
        raw_token = get_cookie(scope, settings.AUTH_ACCESS_COOKIE_NAME)  # из заголовка Cookie
        user = await database_sync_to_async(resolve_user_from_jwt)(raw_token)
        scope['user'] = user or AnonymousUser()
        return await self.inner(scope, receive, send)

resolve_user_from_jwt() (common/websockets/jwt_auth.py) зеркалит CustomJWTAuthentication.get_validated_token() из раздела 3: проверяет подпись/срок через AccessToken(raw_token), отклоняет magic-link токены, проверяет ревокацию сессии через тот же Redis-кэш.

async def connect(self):

13Хранение токенов на фронтенде

zhancareai/src/utils/api.ts
const ACCESS_TOKEN_KEY  = "access_token";
const REFRESH_TOKEN_KEY = "refresh_token";
const USER_KEY          = "user";

export const getAccessToken = (): string | null =>
  typeof window === "undefined" ? null : localStorage.getItem(ACCESS_TOKEN_KEY);

export const setTokens = (accessToken: string, refreshToken: string) => {
  localStorage.setItem(ACCESS_TOKEN_KEY, accessToken);
  localStorage.setItem(REFRESH_TOKEN_KEY, refreshToken);
};

export const clearTokens = () => {
  localStorage.removeItem(ACCESS_TOKEN_KEY);
  localStorage.removeItem(REFRESH_TOKEN_KEY);
  localStorage.removeItem(USER_KEY);
};
КлючХранилищеНазначение
access_tokenlocalStorageПодвешивается в заголовок Authorization (обязателен для Tauri-приложения)
refresh_tokenlocalStorageИспользуется только эндпоинтом обновления
userlocalStorageКэш профиля для мгновенной гидратации UI без ожидания API
zha_authCookie (не httpOnly)Флаг для Next.js Middleware — сам по себе не несёт токена
zha_accesshttpOnly Cookie (новое)Access-токен; недоступен из JS, недосягаем для XSS. Secure в проде, SameSite=Lax, Domain=.zhan.care
zha_refreshhttpOnly Cookie (новое)Refresh-токен; Path=/api/v1/auth/ — браузер шлёт его только на auth-эндпоинты
access_token / refresh_tokensessionStorageТолько для гостевых magic-link сессий — стирается при закрытии вкладки
Добавлен httpOnly cookie слой (dual-mode): login/logout/token/refresh теперь дополнительно выставляют/чистят zha_access и zha_refresh рядом с прежним JSON-телом — ничего из localStorage-флоу не убрано. CustomJWTAuthentication.authenticate() (раздел 3) сначала пробует заголовок Authorization, и только если его нет — читает cookie. Это значит: ZhanCare AI и Academy-фронтенд могут постепенно переходить на cookie-аутентификацию (XSS больше не может украсть токен из JS), а Tauri-приложение и zhancare.app/tauri.localhost (другой регистрируемый домен, не может получить .zhan.care-cookie) продолжают работать через заголовок без единой строчки изменений.
Почему localStorage не убран совсем: ~17 компонентов в коде читают localStorage.getItem('access_token') напрямую, плюс есть второй, полностью параллельный фронтенд (zhancare-academy-refined, academy.zhan.care) с тем же паттерном. Полная миграция на cookie-only — отдельная задача после того, как cookie-флоу подтвердит себя в проде несколько дней.

14Axios-интерсепторы и автоматический рефреш

zhancareai/src/utils/api.ts

Request-интерсептор — подвешивает токен

axiosInstance.interceptors.request.use((config) => {
  const isAuthEndpoint = config.url?.includes("/auth/login")
                       || config.url?.includes("/auth/register");

  if (!isAuthEndpoint) {
    const token = getAccessToken();
    if (token) config.headers.Authorization = `Bearer ${token}`;
  }
  config.withCredentials = true;
  return config;
});

Логин/регистрация исключены сознательно — иначе протухший токен из прошлой сессии полетит в заголовке нового логина и приведёт к ложному 401.

Response-интерсептор — рефреш при 401 без дублирования запросов

let refreshPromise: Promise<string> | null = null;

axiosInstance.interceptors.response.use(
  (response) => response,
  async (error) => {
    const originalRequest = error.config;
    const isAuthRequest = /* .../auth/login|register|refresh */;

    if (error.response?.status === 401 && !isAuthRequest && !originalRequest._retry) {
      originalRequest._retry = true;

      try {
        // если рефреш уже идёт от другого параллельного запроса — ждём его,
        // а не запускаем второй POST /token/refresh/
        if (!refreshPromise) refreshPromise = refreshAccessToken();

        const newAccessToken = await refreshPromise;
        refreshPromise = null;

        originalRequest.headers.Authorization = `Bearer ${newAccessToken}`;
        return axiosInstance(originalRequest);  // повторяем исходный запрос

      } catch (refreshError) {
        refreshPromise = null;
        clearTokens();
        window.dispatchEvent(new CustomEvent('auth:logout', {
          detail: { message: '⏳ Ваша сессия истекла...' }
        }));
        return Promise.reject(refreshError);
      }
    }
    return Promise.reject(error);
  }
);
Решение race condition: если на странице параллельно летит 5 запросов и все получают 401 одновременно (токен истёк), только первый создаст refreshPromise — остальные 4 просто await тот же промис и переиспользуют новый токен. Без этого механизма backend получил бы 5 одновременных запросов на /token/refresh/, из которых из-за ROTATE_REFRESH_TOKENS только первый завершился бы успешно, а остальные 4 — ошибкой «токен уже в blacklist».

Сама функция обновления токена

async function refreshAccessToken(): Promise<string> {
  const refreshToken = getRefreshToken();
  if (!refreshToken) throw new Error("No refresh token found");

  // axiosInstance, а не голый axios — иначе withCredentials:true не применяется
  // и httpOnly cookie zha_access/zha_refresh не уедут/не придут (см. ниже)
  const { data } = await axiosInstance.post(`/auth/token/refresh/`, { refresh: refreshToken });

  localStorage.setItem(ACCESS_TOKEN_KEY, data.access);
  if (data.refresh) localStorage.setItem(REFRESH_TOKEN_KEY, data.refresh);  // ротация

  // синхронизируем React-состояние AuthContext с новым токеном
  window.dispatchEvent(new CustomEvent('auth:token-refreshed', { detail: { access: data.access } }));

  return data.access;
}
Найденный и исправленный баг: эта функция раньше вызывала axios.post(...) напрямую (не axiosInstance) — то есть без withCredentials: true, который настроен на самом instance'е. Если бы фронтенд переходил на cookie-based рефреш, эта функция тихо не отправляла и не получала бы httpOnly cookies, в то время как остальной код проекта думал бы, что cookie-флоу работает. Исправлено в этом же проходе вместе с разделом 13.
Эквивалент в zhancare-academy-refined/lib/api/base.ts (второй, параллельный фронтенд на academy.zhan.care) использует fetch(), а не axios — там не было поля withCredentials вообще, и нужно было явно добавить credentials: "include" на все три вызова fetch() внутри fetchWithAuth()/_doRefresh(), иначе fetch по умолчанию не шлёт cookies на cross-origin запросы.

16Middleware и защита роутов

zhancareai/src/middleware.ts
const PROTECTED_PREFIXES = [
  "/admin", "/doctor", "/nurse", "/patient", "/profile",
  "/video-call", "/appointments", "/documents", "/history", "/chat",
];

export function middleware(request: NextRequest) {
  const { pathname } = request.nextUrl;
  const isAuthenticated = !!request.cookies.get("zha_auth")?.value;

  if (pathname.startsWith("/login") && isAuthenticated) {
    return NextResponse.redirect(new URL("/profile", request.url));
  }

  if (PROTECTED_PREFIXES.some(p => pathname.startsWith(p)) && !isAuthenticated) {
    const loginUrl = new URL("/login", request.url);
    loginUrl.searchParams.set("next", pathname);
    return NextResponse.redirect(loginUrl);
  }

  return NextResponse.next();
}
Это не реальная защита данных — middleware смотрит только на наличие куки zha_auth=1, которая не содержит и не проверяет сам JWT. Её единственная задача — UX (не показывать форму логина авторизованному пользователю, редиректить неавторизованного до того, как страница начнёт грузить данные). Реальная авторизация и проверка прав — всегда на backend, через CustomJWTAuthentication + permission classes DRF.

18Безопасность: что сделано хорошо и что стоит улучшить

✓ Сделано хорошо

  • Короткий access token (15 мин) ограничивает окно атаки
  • Ротация refresh-токена + немедленный blacklist старого
  • Сессии привязаны к устройству — можно отозвать конкретный девайс
  • Magic-link токен чистится из URL до запроса к API
  • sessionStorage для гостевых консультаций (не остаётся после закрытия вкладки)
  • Серилизация конкурентных refresh-запросов (единый refreshPromise)
  • (новое) Rate limiting на login/register (5/мин) и password-reset (3/мин)
  • (новое) Magic-link токен не принимается как обычный bearer-токен
  • (новое) Проверка сессии кэшируется в Redis на 45с, с явной инвалидацией на logout/refresh
  • (новое) httpOnly cookies для access/refresh — dual-mode рядом с localStorage
  • (новое) WebSocket аутентифицируется по JWT-cookie до accept(), с AllowedOriginValidator
  • (новое) Удалён мёртвый неаутентифицированный legacy WS-консьюмер

⚠ Осталось улучшить

  • localStorage всё ещё первичен для ~17 компонентов и второго фронтенда (academy) — полная миграция на cookie-only впереди, после нескольких дней стабильной работы dual-mode в проде
  • logout() молча не отзывает сессию на сервере при некорректном refresh_token от клиента (узкий edge case, см. раздел 7)
  • Throttle-скоуп auth_login общий для login и register — burst регистраций с одного IP может затроттлить и логины оттуда же
  • Явной CSRF-проверки на DRF-эндпоинтах нет (DRF оборачивает все view в csrf_exempt) — защита от CSRF держится на SameSite=Lax у новых cookie, а не на токене в заголовке
  • Вне рамок этой задачи, но важно: найдены захардкоженные секреты в settings.py (включая SECRET_KEY, который подписывает JWT), уже закоммиченные в git — требуют ротации и отдельного решения
